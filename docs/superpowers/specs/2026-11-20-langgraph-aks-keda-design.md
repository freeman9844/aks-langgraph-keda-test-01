# AKS에서 LangGraph 실행 수 기반 Pod 확장·축소 검증

## 목적과 범위

새 테스트용 AKS에서 실제 LangGraph Run 개수가 Azure Managed Prometheus에 수집되고, KEDA가 같은 지표로 Deployment의 복제본 수를 조정하는지 확인한다. TTFT 개선, 실제 LLM 호출, 운영 용량 산정, 노드 자동 증설은 검증하지 않는다.

## 검토한 접근

- **선택: 고정 노드 풀.** 테스트 Pod 3개와 시스템 구성 요소가 동시에 들어갈 용량을 사전에 확보한다. 지표 전달과 Pod 확장 자체를 노드 확보 지연과 분리할 수 있다.
- **제외: Cluster Autoscaler까지 포함.** Pending Pod가 새 노드에서 기동하는 동작을 볼 수 있지만, 비용과 검증 변수가 늘어나 이번 목적에 맞지 않는다.

## 실험 구성

- 전용 리소스 그룹에 AKS, 이미지 저장용 ACR, Azure Monitor workspace 및 필요한 모니터링 리소스를 구성한다. AKS의 Managed Prometheus, KEDA, Workload Identity를 사용한다. 실험 앱과 부하 발생기는 별도 네임스페이스에 두고 공개 인그레스는 만들지 않는다.
- 단일 프로세스 Python Pod에서 실제 LangGraph를 실행한다. 그래프 노드는 외부 모델 대신 비동기 대기하고, 최초 Pod 하나가 최소 6개 Run을 동시에 실행할 수 있어야 한다. 실행 구간 진입·종료 시 `agent_runs_active` Gauge를 증감하며 오류·취소 시에도 감소시킨다. 테스트 클라이언트가 실행을 해제할 수 있게 하되 안전을 위해 최장 실행 시간도 둔다.
- 각 Pod의 `/metrics`를 개별 수집한다. 같은 Run을 중복 집계하지 않도록 스크레이프 경로를 하나만 구성한다. KEDA는 Workload Identity와 조회 권한으로 workspace의 Prometheus 쿼리 엔드포인트를 읽는다. 대상 클러스터·네임스페이스·앱의 시계열만 합산한다.
- KEDA Prometheus 트리거는 `AverageValue`, 목표 2 Run/Pod, 최소 1·최대 4 Pod로 설정한다. 테스트 클러스터와 앱은 처음에는 Ready Pod 1개로 시작한다. 결측·인증 오류를 정상적인 0으로 판정하지 않는다.

## 통과 기준

1. **기본 상태:** 앱 Pod가 Ready 1개이고 workspace에서 값 **0**을 실제로 조회한다. 빈 결과는 통과가 아니다.
2. **확장:** 처음의 한 Pod에 Run 6개를 시작하고 유지한다. 앱의 실제 동시 실행 수, workspace 합계 **6**, HPA 희망 복제본 **3**, Deployment Ready **3**을 각각 확인한다. 시각을 기록해 수집 지연과 기동 지연을 구분한다.
3. **새 Pod 검증:** 기존 Run의 이동은 기대하지 않는다. 새로 생긴 Pod 하나를 대상으로 짧은 Run을 실행해 해당 Pod가 처리 가능한지 별도로 확인한다. 이 요청은 6 Run 기준 확장 판정이 끝난 뒤에만 보낸다.
4. **축소:** 모든 Run을 종료한 뒤 workspace에서 실제 **0**을 확인한다. HPA 축소 안정화 시간이 지난 후 희망·Ready 복제본이 **1**로 돌아오고 노드 수는 실험 내내 그대로인지 확인한다.
5. **종료:** 희망 복제본, Ready 수, 노드 수, PromQL 결과와 시각을 기록한다. 실제 Azure 리소스 생성 전 대상 구독·리전·예상 비용을 확인하고, 검증이 끝나면 전용 리소스 그룹 및 실험용 권한을 정리한다.
